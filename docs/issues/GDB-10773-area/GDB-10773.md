# GDB-10773 — inaccurate metric calculations (area / distance)

- **Jira:** https://graphwise.atlassian.net/browse/GDB-10773x
- **Pulled:** 2026-08-04

## Evaluation case (Nata’s UPD, 3 Aug 2026) — primary

Anonymized ACCORD **Tegel land-parcel** extract (URIs rewritten to `graphdb.example.com`). Purpose: check that GraphDB’s area calculation on engineering-CRS WKT matches independent oracles.

### What’s in the TTL

| Field | Role |
|-------|------|
| `geo:asWKT` | Polygon in **EPSG:25833** (easting/northing metres) |
| `geo:asGeoJSON` | Same geometry also as GeoJSON (WGS84 lon/lat) |
| `geo:hasMetricArea` | Area precomputed with **GDAL** (not GraphDB) — reference |
| `xp:plotCoverage` | Source plot coverage from planning files — second reference |
| `xp:floorAreaTotal` | Floor-area budget (not the polygon area oracle) |

Rough counts: ~176 geometries with WKT + `hasMetricArea`; ~47 features also carry `xp:plotCoverage`.


### Pass criterion

For each parcel geometry, GraphDB-computed area (e.g. `geoext:area` / GeoSPARQL metric area) should **match** `geo:hasMetricArea` (and stay within ~1 m² of `xp:plotCoverage` where present) **when working in EPSG:25833**

Example check query shape:

```sparql
PREFIX geo: <http://www.opengis.net/ont/geosparql#>
PREFIX geoext: <http://rdf.useekm.com/ext#>
PREFIX xp: <https://graphdb.accordproject.eu/resource/xplanung/>

SELECT ?f ?plotCoverage ?gdalArea ?gdbArea ?deltaGdal WHERE {
  ?f geo:hasDefaultGeometry ?g ;
     xp:plotCoverage ?plotCoverage .
  ?g geo:asWKT ?wkt ;
     geo:hasMetricArea ?gdalArea .
  BIND(geoext:area(?wkt) AS ?gdbArea)
  BIND(abs(?gdbArea - ?gdalArea) AS ?deltaGdal)
}
ORDER BY DESC(?deltaGdal)
```

(Adjust the bind to whatever metric-area function v2 exposes.)

### Sample row from the file

Feature `…/GML_002fefc8-…`:

- `xp:plotCoverage` = **365.0**
- `geo:hasMetricArea` = **364.3203** (~0.7 m² off source — in Nata’s ~1 m² band)
- WKT CRS = `EPSG:25833`

GraphDB should land next to **364.32**, not a WGS84-projected distortion.

## Background (why this fails on v1)

Triona / Lars Wikström first reported wrong `geof:distance` on **EPSG:3006** (expect 5 m → got ~3.24; expect 100 m → got ~66.7). Root cause: plugin converts everything to WGS84 before metric ops ([GDB-9428](https://graphwise.atlassian.net/browse/GDB-9428)). Same failure mode hits Tegel area checks and later EPSG:3011 building-vs-regulation distance (~100 m vs QGIS).

## What “fixed” looks like

1. Load `GDB-10773.ttl`, enable GeoSPARQL.
2. Area (and distance) computed in the literal’s CRS (25833), aligned with `geo:hasMetricArea`.
3. Optional: keep the original Triona 3–4–5 / 100 m point fixtures as unit tests alongside this parcel set.
