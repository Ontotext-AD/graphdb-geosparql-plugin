# GDB-9378 — GeoSPARQL GML literals don't work (ACCORD: Germany, Spain)

- **Jira:** https://graphwise.atlassian.net/browse/GDB-9378
- **Pulled:** 2026-08-04

## Summary

ACCORD urban-planning data uses `geo:asGML` (not WKT). On GraphDB with GeoSPARQL enabled, **topological magic properties and calculation functions ignore / fail on GML literals** — they return unbound or never match. The same operations work for WKT. Documented GML support (since ~2016) is a regression: even the docs’ own GML `geof:distance` example leaves the GML binding unbound while the WKT twin works.

## Why it matters for evaluation

- Real AECO / ACCORD data is GML with engineering CRSes (**EPSG:25833** DE/Tegel, **EPSG:25831** ES/Malgrat).
- Constructs go beyond simple polygons: `MultiSurface`, `Surface` + `PolygonPatch`, `posList@count`.
- Until GML works natively, ACCORD converted strings to WKT (scripts in [Tegel-scripts](https://github.com/Accord-Project/Tegel-scripts)) and often disabled the plugin for calculations.

## Observed failures

1. **Magic properties on GML geometries** — `geo:sfEquals` / `geo:sfContains` (and similar) do not behave as if the geometry exists; optional patterns stay empty.
2. **Functions on GML** — `geof:sfEquals`, `geof:sfContains`, `geoext:area`, `geof:envelope` return unbound when the argument is a `geo:gmlLiteral`.
3. **Docs regression** — binding `geof:distance` on two GML points vs two WKT points: WKT binds, GML does not (reproduced on GDB 9.10.3 and 10.4.0).

### Example query shape (ACCORD Tegel)

```sparql
PREFIX xp: <https://graphdb.accordproject.eu/resource/xplanung/>
PREFIX geo: <http://www.opengis.net/ont/geosparql#>
PREFIX geof: <http://www.opengis.net/def/function/geosparql/>
PREFIX geoext: <http://rdf.useekm.com/ext#>

select * {
  ?x a xp:BuildingSubArea ; geo:hasDefaultGeometry/geo:asGML ?geo .
  bind(geoext:area(?geo) as ?area)
  bind(geof:envelope(?geo) as ?bbox)
}
```

Expected: `?area` / `?bbox` bound. Actual: unbound.

### Minimal docs-style oracle (WKT vs GML)

```sparql
PREFIX uom: <http://www.opengis.net/def/uom/OGC/1.0/>
PREFIX geof: <http://www.opengis.net/def/function/geosparql/>
PREFIX geo: <http://www.opengis.net/ont/geosparql#>

select * WHERE {
  BIND (geof:distance('''Point(1 1)'''^^geo:wktLiteral,
                      '''Point(2 2)'''^^geo:wktLiteral, uom:metre) as ?distWkt) .
  BIND (geof:distance('''<gml:Point><gml:pos>1 1</gml:pos></gml:Point>'''^^geo:gmlLiteral,
                      '''<gml:Point><gml:pos>2 2</gml:pos></gml:Point>'''^^geo:gmlLiteral, uom:metre) as ?distGml) .
}
```

| Binding | Expected | Actual (v1) |
|---------|----------|-------------|
| `?distWkt` | bound (√2-ish metres) | bound |
| `?distGml` | same as WKT | **unbound** |

## Geometry shapes to cover

**Germany (Tegel) — EPSG:25833** — `gml:MultiSurface` → `Polygon` → `LinearRing` / `posList` (large parcel footprint).

**Spain (Malgrat) — EPSG:25831** — `gml:MultiSurface` → `gml:Surface` → `gml:PolygonPatch` with `posList srsDimension="2" count="…"`. More complex serialization than Tegel.

Full literal samples are in the Jira comments (2024-01-25, Vladimir Alexiev).

## What “fixed” looks like

- `geo:gmlLiteral` accepted by topological functions and magic properties the same way as WKT.
- Complex GML (`MultiSurface`, `PolygonPatch`) parsed without requiring offline GML→WKT conversion.
- CRS on `srsName` preserved for metric ops (ties to GDB-9428 / GDB-9450), not silently coerced in a way that breaks planning checks.
